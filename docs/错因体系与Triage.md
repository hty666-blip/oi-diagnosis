# 错因体系 v2：双轴模型与 Triage 分诊

| 项目 | 内容 |
|---|---|
| 版本 | v2.0（修订 [需求分析 §4.1](需求分析.md) 的三层错因体系） |
| 触发 | 一个真实观察：**初学者犯的错，11 类 M 编码装不下** |
| 结论 | 你的判断对，但要改两件事：加一个**性质轴（P）**，以及把"判断"交给**规则优先的分诊节点**，而不是一个自由发挥的 Agent |

---

## 0. 结论先行

| 你的判断 | 我的回应 |
|---|---|
| "人会犯各种各样的错，11 类不够" | ✅ 对。M 编码是**技术机制**分类，缺一个**教育性质**分类 |
| "中英文符号这种也算错" | ✅ 对，而且它应该**单列一档**：P0 表层错误，和"算法错"完全不是一回事 |
| "单独一个 agent 判断是什么错误" | ⚠️ 半对。**需要一个独立的判定环节（Triage）**，但它的实现应该**规则优先**，LLM 只做兜底 |
| "判断是格式错误还是方法错误，再给对应结果" | ✅ 完全正确。这就是**分诊 + 路由**，是省成本和提体验的关键 |

一句话：**加一个维度（P），加一个节点（Triage），但不加一个自由 Agent。**

## 1. 现有 M 编码为什么不够

我那套 `M01 溢出 / M02 数组 / M11 工程习惯` 是**工程师视角**的分类，回答"错在哪个技术点"。但下面这些初学者最常见的错误，它装得很别扭：

| 真实错误 | 塞进 M 表会变成 | 问题 |
|---|---|---|
| `using namespace std；`（中文分号） | M11 工程习惯 | 这不是"习惯不好"，是**输入法没切**，10 秒能改对 |
| `#include <iosteam>`（拼错） | M11 | 同上，纯笔误 |
| `int mian()` | M11 | 同上 |
| `cout << a` 但没 `#include <iostream>` | M08 题意？ | 完全对不上 |
| 变量名写成 `sum` 和 `ans` 混用 | M11 | 其实多半是 P2 实现细节 |
| 数组开在 `main` 里 1e5 导致爆栈 | M02 | 机制对，但学生是**不知道栈空间有限**（P1 概念缺失） |

**根本问题**：M 回答"错在哪个技术点"，但没回答三个教学上更要紧的问题：

1. **这个错有多深？**（笔误 vs 概念缺失 vs 算法错）
2. **该谁来处理？**（规则/编译器就能修 vs 需要老师讲 20 分钟）
3. **讲了有没有用？**（中文分号讲 10 秒就懂，贪心不成立要讲一节课）

所以需要第二个轴。

## 2. 双轴模型：机制 M × 性质 P

### 2.1 性质轴（P）——新增

| 编码 | 名称 | 典型例子 | 谁判定 | 教学动作 | 成本 |
|---|---|---|---|---|---|
| **P0** | 表层 / 输入法 | 中文分号、全角括号、全角空格、BOM、中文引号、拼写错、大小写 | **规则（100% 确定）** | 一句话指出 + **自动修复** | ~0 |
| **P1** | 语法 / 语言规则 | 忘 `#include`、类型不匹配、括号不配对、作用域、函数签名 | 规则（编译日志映射）+ 少量模型 | 报错翻译 + 知识卡链接 | 低 |
| **P2** | 实现细节 | 边界、越界、初始化、取模、精度、多测清空 | 沙箱 + 静态分析 | 反例 + 定位提示 | 中 |
| **P3** | 算法 / 模型 | 复杂度选错、贪心不成立、DP 状态错、图论建模错 | 对拍 + 复杂度探测 | 深度诊断 + 变式训练 | 高 |
| **P4** | 题意理解 | 读错输入格式、漏条件、输出格式不符 | 模型（对照题面） | 重读题 + 关键句标注 | 中 |
| **P5** | 策略 / 习惯 | 不打部分分、不测样例、不检查边界、时间分配 | 画像 + 行为数据 | 教练介入 + 训练计划 | 低 |

### 2.2 两个轴是正交的，不是一一对应

| 例子 | M 编码 | P 编码 | 说明 |
|---|---|---|---|
| `long long` 写成 `int`，n=1e5 | M01 | **P2** | 会写，疏忽 |
| 不知道 `int` 有范围 | M01 | **P1** | 概念缺失 |
| 数组开 1e4 但题面 n=1e5 | M02 | **P2** | 没看数据范围 |
| 不知道要按 n 开数组 | M02 | **P1** | 概念缺失 |
| `sort` 比较器写 `<=` | M10 | **P3** | 不知道严格弱序（属于算法常识） |

**同一个 M 编码，P 不同，教学动作完全不同。** 判定 P 需要上下文——正好用上学生画像（这个知识点他以前错过吗？掌握度多少？）。

> 这就是为什么 P 的判定不能只看代码，还要看历史。也是为什么 Triage 必须拿得到 `StudentProfile`。

## 3. 为什么 P0/P1 必须规则判定（不是"也可以"）

有人会说："让 LLM 看一眼不就知道是不是全角符号了吗？"——不行，四个理由：

| 理由 | 说明 |
|---|---|
| **确定性** | 字符集检查是 100% 可判的；LLM 对"字符级"细节不稳定，同一个文件两次可能给出不同结论 |
| **成本** | 初学者提交里 P0/P1 占比很高，每条都调模型是纯浪费 |
| **可解释** | "第 3 行第 12 列是中文分号 U+FF1B" 比 "你可能用了中文符号" 有用一百倍 |
| **LLM 的盲区** | 让模型判断全角符号，它常会说"这段代码看起来没问题"——因为**语义上确实没问题**，问题在字符编码层 |

**原则**：**能确定性判定的，绝不交给模型。** 这和我们"证据优先"的整体设计是一致的——规则产出的也是证据，而且是最硬的那种。

## 4. Triage 分诊节点设计

### 4.1 位置

```
INGEST → GUARD → 【TRIAGE】 → PARSE → ROUTE → EVIDENCE → DIAGNOSE → ...
                     │
                     ├─ P0 命中 → 直接返回「秒回修复」，不进流水线
                     └─ 无 P0/P1 → 继续
```

插在 `GUARD` 之后、`PARSE` 之前：**越早分流越省钱**（PARSE 要调模型）。

### 4.2 输入 / 输出契约

```json
// 输入：源码 + 可选编译日志 + 学生画像
// 输出：
{
  "verdict": "CE",
  "findings": [
    {"p": "P0", "m": null, "line": 3, "col": 12,
     "code": "P0-FULLWIDTH", "char": "；",
     "message": "第 3 行第 12 列是中文分号，C++ 只认英文 ;",
     "autofix": ";", "confidence": 1.0},
    {"p": "P2", "m": "M01", "line": 8, "col": 5,
     "code": "M01-INT-OVERFLOW", "message": "sum 是 int，但最大和约 1e14",
     "confidence": 0.88}
  ],
  "route": "fast_fix" | "syntax_help" | "full_pipeline" | "human",
  "minimal_actionable": "P0 第 3 行",
  "degraded": []
}
```

### 4.3 三级判定（规则 → 编译日志 → 模型）

| 级 | 手段 | 覆盖 | 成本 | 失败处理 |
|---|---|---|---|---|
| L1 | **字符级扫描**（`surface_lint`） | P0 全量 | ~1ms | — |
| L2 | **编译日志映射**（GCC 报错 → 人话） | P1 大头 | ~0 | 未命中转 L3 |
| L3 | **模型兜底**（仅当 L1/L2 无结论且代码能编译） | P4/P5 与疑难 | 中 | 转人工 |

注意 L3 的触发条件很窄：**代码能编译、P0/P1 都没命中**，说明错误在语义层，才值得调模型。

### 4.4 路由表

| 命中 | route | 动作 | 时延 | 成本 |
|---|---|---|---|---|
| 只有 P0 | `fast_fix` | 列出全部 + 给「一键修复」+ 重新提交 | < 200ms | ¥0 |
| P0 + P1 | `fast_fix` | 先修 P0，再翻译 P1 报错 | < 500ms | ¥0 |
| 只有 P1 | `syntax_help` | 报错翻译 + 知识卡（RAG） | ~2s | 极低 |
| 编译通过 | `full_pipeline` | 走原诊断流水线 | 8~45s | 正常 |
| 规则与模型冲突 | `human` | 转教练 | — | — |

**这才是真正省钱的地方**：假设初学者提交中 40% 是 P0/P1，这部分从"45 秒 + ¥0.3"变成"0.5 秒 + ¥0"，整体成本直接砍一半。

## 5. 全角 / 输入法错误：可检测、可自动修复

### 5.1 关键设计：只在"代码区"报错

中文出现在**字符串和注释里是合法的**：

```cpp
cout << "和是：" << a + b;   // 这个「：」完全没问题
```

所以扫描器必须做**状态机**（code / string / char / line_comment / block_comment），否则会产生大量误报——误报比漏报更伤害信任。

### 5.2 字符表（节选）

| 全角 | 半角 | Unicode |
|---|---|---|
| `；` | `;` | U+FF1B |
| `，` | `,` | U+FF0C |
| `（）` | `()` | U+FF08/09 |
| `｛｝` | `{}` | U+FF5B/5D |
| `“”` | `"` | U+201C/201D |
| `：` | `:` | U+FF1A |
| `　`（全角空格） | 空格 | U+3000 |
| BOM | 无 | U+FEFF |

### 5.3 实测（工具已跑通）

输入 `examples/bad_fullwidth.cpp`：

```cpp
#include <iostream>
using namespace std；
int main（）｛
    int a， b；
    cin >> a >> b；
    cout << "和是：" << a + b << endl；
    return 0；
｝
```

输出：

```
发现 10 个表层问题：
  [P0] 第 2 行 第 20 列  中文/全角符号「；」不能用于 C++ 语法
         U+FF1B  →  改成英文半角「;」
  [P0] 第 3 行 第 9 列  中文/全角符号「（」...
  ...
```

自动修复后：

```cpp
#include <iostream>
using namespace std;
int main(){
    int a, b;
    cin >> a >> b;
    cout << "和是：" << a + b << endl;   // ← 字符串里的中文原样保留 ✅
    return 0;
}
```

**这就是"啊哈时刻"**：学生点一下按钮，10 个错全没了，而且他立刻明白"哦，是输入法"。

### 5.4 产品化：一键修复

按钮文案建议：

> **发现 10 处中文标点，已自动修正。**（字符串里的中文没有动）
> [ 应用修复并重新提交 ]

**注意**：自动修复必须**只改代码区**，且修复后要**重新走一遍 Triage**（修完 P0，可能暴露 P1）。

## 6. 编译器报错翻译（GCC → 人话）

初学者最崩溃的一行：

```
error: stray '\357' in program
```

这其实是"文件里有非 ASCII 字节"（全角字符或 BOM），但没人看得懂。翻译表：

| GCC 原文 | 系统给出的意思 | 怎么办 |
|---|---|---|
| `stray '\357' in program` | 代码里有编译器不认识的非 ASCII 字符，最常见是中文标点或 BOM | 检查该行全角符号 |
| `expected ';' before '}'` | 上一行结尾少了分号 | 看**报错位置的上一行末尾** |
| `'cout' was not declared in this scope` | 用了未声明的名字 | 确认 `#include <iostream>` 和 `using namespace std;` |
| `expected '}' at end of input` | 括号没配对，少一个 `}` | 从 `main` 开始逐层查 |
| `invalid conversion from 'const char*' to 'int'` | 把字符串当整数用了 | 检查变量类型与输入方式 |

**这些全部是规则可做的**，不需要模型。工具里已经带了这个映射（`--gcc-log`）。

## 7. 「最小可行动错误」原则

一次 CE 可能有 10 个错误。全列出来会**吓退初学者**（认知负荷理论：一次只能处理一个点）。

规则：

1. **全部列出**（面板里给完整清单，方便修）；
2. **只讲最靠前的一个**（P0 优先，因为它可能掩盖后面所有错误）；
3. 修完 → **重新分诊**（re-triage），再看下一个。

```
你有 10 处中文标点，先修这个：
  第 2 行：using namespace std；  →  std;
修好之后我们再看下一个。
```

这比"你这里错了、那里也错了"友好得多，也比"一次性给 10 条修改建议"有效得多。

## 8. 对评测的影响：M × P 双维覆盖

原来的"11 类 M 覆盖"要升级成**双维**：

| 维度 | 资产 | 怎么来 | 规模 |
|---|---|---|---|
| **M（机制）** | 题目探针 | 按探针矩阵**设计** | 20~40 道题 |
| **P（性质）** | 提交样本 fixtures | **收集/构造**学生代码 | 200+ 条 |

关键洞察：**P0/P1 的样本不需要题目**——一段坏代码 + 编译器输出就够了。所以 fixtures 成本极低，可以很快做到 200 条（每类 20 条：全角分号/括号/引号/空格/BOM/拼写/忘 include/括号不配对…）。

新指标：

| 指标 | 定义 | 门槛 |
|---|---|---|
| 分诊准确率 | P 档位判定与人工标注一致 | ≥ 95%（P0 应 100%） |
| 路由准确率 | 该走快路径的没走全流水线 / 反之 | ≥ 90% |
| 自动修复采纳率 | 学生点了"应用修复"的比例 | ≥ 70% |
| 快路径占比 | 走 `fast_fix`/`syntax_help` 的提交比例 | 观测值（估 40%+） |

## 11. 一句话给答辩

> **错因不是一个维度。** 机制轴（M）回答"错在哪"，性质轴（P）回答"错多深、该谁管、值不值得深挖"。
> 分诊用规则做确定性判断，只在语义层才动用模型——**既不把笔误当算法错，也不把算法错当笔误**。
