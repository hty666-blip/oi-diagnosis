## 0. 结论先行

### 0.1 应该"直接集成"的 5 个

| 项目 | 许可 | 用在哪儿 | 我们怎么用 |
|---|---|---|---|
| **go-judge** | MIT | 沙箱执行 | **唯一放进生产链路的重组件**。FastAPI 调 REST，补编译脚本 + 逐点证据采集 |
| **LangGraph** | MIT | 编排 | StateGraph 管流程，checkpoint 管续跑，interrupt 管人工接管（见 ADR-002 修订） |
| **Langfuse** | MIT + `ee/` 商业 | 可观测 | Trace / cost / latency / prompt 版本 / dataset 评测；**只用核心，避开 `ee/`** |
| **OI Wiki** | CC BY-SA 4.0 + SATA | RAG 语料 | 中文 OI 知识层最佳；按标题分块、保留公式代码、带引用、署名 + Star |
| **pyBKT** | MIT | 学情建模 | 先做可解释 BKT 基线，再扩展"知识点 × 错误类型"双维 |

> 备选：Windows 为主、不想写编译脚本 → 用 **Judge0**（GPL-3.0）替代 go-judge；但它只"运行代码"，不做 OI 判题。**二者选其一，不要同时引入。**

### 0.2 应该"借鉴设计而非引入依赖"的 3 个

| 项目 | 借鉴什么 | 为什么不直接用 |
|---|---|---|
| **Agentless** | `localize → repair → validate` 三段式，改成 `定位 → 诊断 → 最小反例 → 验证` | 面向 repo 级 patch，不是单文件 OI；但骨架极适合我们（便宜、可控、可解释） |
| **Reflexion** | "语言化反思 + 情节记忆" | 把 WA/TLE 变成学生模型里的"错因反思"，按知识点检索；不依赖其代码 |
| **CodeAid** | "不直接给答案"的提示分层与交互 | **无 license**，只能学设计，不能复制代码 |

### 0.3 没有现成轮子、必须自研的 4 块（= 毕设创新点）

1. **OI 错因本体与判题证据链**：`AC/WA/TLE/RE/MLE` 太粗，要能计算到"溢出/边界/多清空/复杂度/建模"；
2. **多 Agent 诊断协议：假设—反例—验证**（含 **evidence gate**：无执行证据不得定因）；
3. **学生模型与提示策略**（知识点树 + 错因库 + 掌握度 + L0~L4 阶梯，永不直接给完整代码）；
4. **评测集与指标**（人工标注错因 + 提示质量 rubric + 答案泄露率）。

> 一句话：**现成轮子覆盖了"执行、编排、观测、知识"，没覆盖"从判题证据到教学诊断的映射"。**

## 4. 七个许可证陷阱（这一节最容易被答辩问到）

| # | 陷阱 | 后果 | 我们的处理 |
|---|---|---|---|
| 1 | **EduChat / CodeAid 无 license** | 默认"保留所有权利"，复制代码/权重即侵权 | 只读思路，不复制；文档里注明"仅参考设计" |
| 2 | **AGPL（Hydro / DMOJ）** | 改后通过公网提供服务须开放源码 | 不 fork；只通过插件/HTTP 边界集成 |
| 3 | **GPL（Judge0 / TutorGPT / isolate）** | 分发衍生作品须开源 | 若用 Judge0，仅内部部署不交付镜像 |
| 4 | **AutoGen 根 LICENSE 是 CC-BY-4.0** | 内容许可，非软件许可，缺专利授权 | 不使用；改用 LangGraph |
| 5 | **Phoenix 是 ELv2** | 禁止作为托管服务转售 | 内部自用可以，或直接选 Langfuse |
| 6 | **Langfuse 是 MIT + `ee/`** | `ee/` 目录商业条款 | 只用核心目录，不引入 `ee/` |
| 7 | **OI Wiki 无根 LICENSE** | GitHub API `license=null`；授权写在 README 版权声明 | 内容按 CC BY-SA 4.0 + SATA 使用；**代码部分授权另论**，引用代码需谨慎 |

> **一条通用经验**：`license=null` 的仓库，**一律按"保留所有权利"处理**。GitHub 上大量高星教育项目都属于这一类。

## 5. 专项：OI Wiki 能不能做 RAG 语料？

**结论：非常适合做"知识层"，不适合做"题目答案库"。**

- **规模**：仓库约 102 MB；官网 14 个一级分区（简介/比赛/工具/语言/算法/搜索/DP/字符串/数学/数据结构/图论/计算几何/杂项/专题），`docs/` 为 MkDocs Markdown 源，含大量 LaTeX 与代码块。
- **最适合的部分**：算法概念、复杂度、题型、**常见错误**（`contest/common-mistakes`）、testlib/Special Judge、语言基础。
- **不适合的部分**：具体题目的标准答案、某题独特 trick、学生个人错题历史。
- **工程建议**：按 H2/H3 分块；公式与代码块单独保留；metadata 加 `section/tags/difficulty/source_url`；检索用 BM25 + embedding 混合；回答必须带引用链接。
- **合规建议**：页脚注明来源与 CC BY-SA 4.0；公开部署时衍生内容同协议共享；给仓库点 Star（SATA 要求）。

## 6. 专项：错题本 / 学情分析有现成轮子吗？

**没有。** 本次核验的 29 个仓库里，**没有一个面向 OI 的"错题本 + 学情分析"开源产品**。G 类只有通用算法库：

- **pyBKT**：小数据可用、可解释，但没有题目模型、错因标注、教师工作流；
- **pyKT**：需要较长提交序列，冷启动与可解释性不如 BKT。

这意味着：错题本的数据模型、错因标签体系、知识点映射、教师复核界面，**全部要自研**——这恰好是毕设能做出差异化的地方，也是"为什么这个项目值得做"的最有力论据。

## 7. 调研如何改写了我们的架构决策

| 架构决策 | 调研前 | 调研后 | 原因 |
|---|---|---|---|
| 编排内核 | 自研 DAG 引擎（~1000 行） | **LangGraph + 自研预算/证据/挂起** | LangGraph 已覆盖 70%，自研要 2~3 周，12 周排期不划算（ADR-002 v1.1） |
| 学情模型 | 简化 BKT 自写 | **pyBKT 基线 + 双维扩展** | 有 MIT 现成实现，省 3~5 天，且论文可对比 |
| 可观测 | 只用 OTel + Prometheus | **加 Langfuse** | 现成的 prompt 版本管理 + dataset 评测，直接支撑实验章节 |
| 沙箱 | 已定 go-judge | **不变** | 结论被证实：唯一建议进生产链路的组件 |
| 题目包 | 已定 A/B/C/D 分级 | **不变** | 题库调研证实 validator 比 testdata 更稀缺 |

## 8. 简历怎么写"基于 X 改进"才不翻车

| 你的实际动作 | 可以写 | 不能写 |
|---|---|---|
| 调用 go-judge 的 REST API | "基于 go-judge 构建评测执行层" | ❌ "改进 go-judge" |
| 用 LangGraph 编排 | "基于 LangGraph 实现多 Agent 状态机" | ❌ "改进 LangGraph" |
| 改 BKT 的状态定义 | ✅ "基于 pyBKT 改进：知识点 × 错误类型双维知识追踪" | — |
| 改 Agentless 的流水线 | ✅ "基于 Agentless 改造：定位—诊断—验证 三段式" | — |

**两个真正站得住的改造点**（有 before/after、有指标）：

1. **基于 pyBKT 的双维知识追踪**
   - 改什么：单一掌握状态 → `知识点掌握 × 错误类型倾向` 双维；用诊断 Agent 的证据更新，而不是只用对/错；
   - 怎么证明：对比 BKT / DKT，报 AUC / RMSE / NLL；消融"有/无诊断证据"。

2. **基于 Agentless 的"定位—诊断—验证"流水线**
   - 改什么：`repair` 换成 `diagnose + hint`，增加最小反例生成与 evidence gate，输出诊断报告而非补丁；
   - 怎么证明：对比 naive CoT / ReAct / 完整多 Agent，报诊断准确率、证据覆盖率、答案泄露率、平均耗时。
