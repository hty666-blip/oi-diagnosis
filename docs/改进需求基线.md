# 错题诊断系统：改进需求基线

版本：2026-10-29；状态：本轮改进基线，优先把核心功能做可靠。旧需求文档保留作历史材料；下列验收规则是目标，是否完成以测试与交付记录为准。

## 1. 产品目标与用户

主要用户是学习 C++ 的信息学竞赛学生，教师负责复核证据不足的诊断。系统解决三件事：说明一次执行实际验证了什么，帮助学生定位下一步检查点，保留修改前后的证据。

本轮目标是可靠的本地教学演示：学生提交代码后，能获得与实际测试范围一致的结果，并用一次真实的修改重提交验证修复。现有仓库不能证明学生或机构已实际使用，也不能证明教学效果。

教师首版只查看本班提交与待复核列表；班级暂以账号的非空 `class_name` 匹配。管理员可查看全部。此规则不是机构多租户模型，不应扩展解释为正式的组织权限管理。

## 2. 核心流程

选题并查看可用测试范围 → 编写或粘贴代码 → 编译与执行 → 查看结果、原始证据和诊断依据 → 按需获得提示 → 修改并再次提交 → 对照执行结果。

一次会话始于一个明确的提交。学生说“改对了”“AC 了”只表示请求验证，不能改变执行事实。验证必须使用同账号、同题的新提交；正式题包测试全部通过后，才能关闭该答疑。公开样例全部通过仍保留“验证不足”的边界。

历史记录应能重新打开题目、代码和证据；导出错题卡必须携带当前账号授权。失败时保留编辑内容，提示可执行的恢复动作。

## 3. 本轮范围与非目标

- P0：判定与测试范围一致；自建题包测试可执行；提交和答疑归属校验；修改重提交验证；停止用聊天次数或口头“AC”更新掌握度；相关回归检查。
- P1：明确的提交谱系、完整历史恢复、教师复核写回与审计、任务重试和并发控制、真实课堂反馈。
- 暂不做：家长周报、认知标签、生成题目、知识图谱、机构多租户、支付与完整 OJ；不以 Agent 数量作为产品能力。
- 保留现有模块化单体；规则和执行器负责事实，模型只提出带依据的解释，模型不可用时仍应显示执行证据。

## 4. 验收标准

| 编号 | 可验收行为 |
| --- | --- |
| A1 | 编译成功但无测试时返回 `NO_TESTS`；样例全过返回 `SAMPLE_PASS`；只有实际执行自建题包测试且全部通过，才可返回 `AC`，同时保留测试范围。 |
| A2 | 提交、证据、诊断、答疑及导出均检查服务端归属。学生仅访问本人内容；教师仅访问同一非空班级学生内容；管理员可访问全部。 |
| A3 | 真实执行失败时显示编译或运行证据、计数与范围；执行器异常不能作为学生代码错误，零次运行不能算通过。 |
| A4 | 口头“AC”不关闭会话；同题新提交的正式测试 `AC` 才能完成验证。异题、他人提交、样例通过或无测试不能完成验证。 |
| A5 | 聊天回复不更新掌握度；一次修复通过也不直接宣称掌握知识点。没有可复核的学习观测事件前，不展示伪精确的掌握结论。 |
| A6 | 诊断的证据引用真实存在，最后一次评审失败不能标记为已确认。模型建议与执行事实分开，模型不可用时仍展示已有证据。 |
| A7 | 自建题包至少验证已知正确程序通过、已知错解失败；测试输入和预期输出成对，缺失或无效题包不能静默降级成“正式测试通过”。 |
| A8 | 通过与改动有关的后端回归、前端构建和关键流程检查，并记录教师写回、任务化等未完成项。 |

## 5. 为什么原方案需要调整

以下为改进前代码与文档核对结果，不表示问题已全部修复。

| 问题 | 证据位置 | 对用户的影响 | 处理 |
| --- | --- | --- | --- |
| 未执行测试也返回 `AC`，公开样例通过与正式测试通过混用 | `backend/app/services/submission_service.py` 的 `decide_verdict` 与 `run` | 错误程序可能被标记正确 | P0：拆分结果与测试范围 |
| 读取提交、证据、诊断和错题卡仅检查登录；答疑无归属校验 | `backend/app/api/v1/submissions.py`、`tutor.py`、`card.py` | 换 ID 可接触他人的学习记录 | P0：统一服务端授权 |
| 教练队列与概览读取全库，没有班级条件 | `backend/app/api/v1/catalog.py` | 教师能看到其他班数据 | P0：按非空班级过滤 |
| 口头“AC”关闭会话，每轮聊天都更新 BKT | `backend/app/agents/tutor.py`、`services/tutor_service.py` | 学习结论由对话措辞和次数制造 | P0：真实重提交验证，暂停聊天驱动更新 |
| `gate_node` 不检查最后一次 `critique.passed` | `backend/app/orchestrator/graph.py` | 结构评审失败仍可能确认结论 | P0：失败不能放行 |
| 反例最小化工具存在，但答疑视图的反例固定为空 | `backend/app/services/tutor_service.py` 的 `_diag_view` | 文档能力超出实际教学链路 | P1：接入后再宣称支持 |
| 教师只有待复核查询，没有修改结论与留痕入口 | `backend/app/api/v1/catalog.py` | “转人工”不是完整复核流程 | P1：实现写回与审计 |
| 历史页只能看摘要，错题卡使用不携带 Bearer 的普通链接 | `web/src/App.tsx` | 无法继续原提交，导出可能未登录 | P0 修复导出；完整历史恢复列 P1 |
| README 混合实现、规划、构造集指标与少量案例结论 | `README.md` 与旧 `docs/需求分析.md` | 容易把演示当实证，把计划当交付 | 保留历史，改为逐项验证记录 |

旧需求示例把 `1+2+3+4` 描述为 `int` 溢出，数值不成立。后续演示必须来自真实执行并保留输入、预期输出、实际输出；不能为叙事编造反例。

## 6. 结果与证据契约

| 结果 | 可说明的事实 | 不能说明的结论 |
| --- | --- | --- |
| `CE` | 指定编译器与参数下编译失败 | 整个解题思路错误 |
| `WA` / `RE` / `TLE` / `MLE` / `OLE` | 某个实际执行的用例不匹配、异常或超限 | 无证据支持的算法根因或认知缺陷 |
| `NO_TESTS` | 编译成功，没有可执行测试 | 代码正确或已经修复 |
| `SAMPLE_PASS` | 当前公开样例全部通过 | 隐藏边界通过或题目已通过 |
| `AC`，范围为题包 | 当前版本题包测试全部通过 | 数学意义上的完全正确、学生独立完成或掌握知识点 |
| 基础设施失败 | 本次验证未完成，可重试 | 学生代码发生 `RE` 或正式测试通过 |

接口、工作台、历史和导出应使用同一组语义。已保存的旧 `AC` 记录不自动升级成正式验证证据；重用结果需要匹配当前执行版本及有效测试范围。

诊断描述至少回答：观察到了什么、依据是哪条证据、建议先查哪一步。规则发现也不能超出规则的适用范围；证据 ID 存在仅证明引用有效，不证明模型解释正确。未知原因应保留未知，不强行分配机制或认知标签。

## 7. 技术取舍与实施顺序

沿用 FastAPI、React、PostgreSQL 及现有执行器，优先修正已有链路。LangGraph 或多个 Agent 是可替换的实现手段；只有在错误率、延迟、成本或可维护性上有可复核收益时，才扩展编排。当前无需新增语言或独立服务。

1. **可信判定**：接入自建题包，拆分无测试、样例通过、题包通过；补充判定与执行失败回归。
2. **可信访问**：统一提交和会话授权，教师数据按班级约束，导出携带认证；验证所有读取与写入入口。
3. **可信修复**：答疑绑定原提交，复用统一提交链路验证新代码，停止口头结案和聊天驱动掌握度。
4. **完整教学**：补充提交谱系、历史恢复、真实反例接入与教师审定；先用本地可复现案例，再邀请真实用户试用。

无需删除已有实验与论文草稿，但它们不能替代软件验收，也不能作为真实用户效果的证据。

## 8. 如何评价改进

- 工程验收记录实际命令、通过/失败数、执行环境与未覆盖场景；新增回归围绕错误行为，而不是复写实现。
- 诊断质量使用版本化评测集，注明构造/真实来源、测试范围、人工标注方式与未能判断的比例。关键字命中率不等于诊断准确率。
- 修复效果可记录“经提示后，后续同题提交的题包测试通过率”。没有观察学生是否接受外部帮助，不能把它称为“独立改对率”。
- 延迟、模型调用量与失败率应来自实际运行日志；原文的效率提升、准确率与秒级承诺均作为待验证假设，不作为当前能力。

## 9. 交付核对入口

| 验收方向 | 代码入口 | 应有证据 |
| --- | --- | --- |
| 判定与范围 | `services/submission_service.py`、题包导入脚本 | 零测试、样例、题包、错解与执行失败回归 |
| 归属与班级 | `api/deps.py`、各提交/答疑/教练接口 | 本人、同班、跨班、无班级、管理员访问用例 |
| 提交验证闭环 | `services/tutor_service.py`、`api/v1/tutor.py` | 口头 AC 无效、异题与他人证据拒绝、正式测试通过才结束 |
| 诊断与呈现 | `orchestrator/graph.py`、`web/src/`、错题卡 | 评审失败不确认、边界文案一致、导出及构建检查 |

路径均相对于仓库根目录；服务文件入口位于 `backend/app/`。实际完成项与限制由本轮交付记录补充，不用需求表勾选代替运行证据。
