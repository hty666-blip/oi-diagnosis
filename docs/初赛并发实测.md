# 初赛并发实测

2026-11-17 在 Windows 开发机（Ryzen 7 5800H、8 核 16 线程、15.4 GiB 内存）使用本机单 API 进程、Docker 中的独立 MySQL 8.4.11。预先建立 100 个合成学生身份，使用已审核发布的原创前缀和填空题。普通读题和确定性评分路径关闭外部模型。各场景暖机后各跑 3 轮，以客户端记录的 p95 展示结果。

| 场景 | 请求数 | p95 | 未通过 |
| --- | ---: | ---: | ---: |
| 100 人同时读题 | 300 | 982 ms | 0 |
| 30 人同时交卷 | 90 | 864 ms | 0 |
| 混合场景读题（70 人） | 210 | 1535 ms | 0 |
| 混合场景交卷（30 人） | 90 | 1915 ms | 0 |

正式记录上表使用仓库中的压测脚本。正误答案各占一半，逐条核对 2 分和 0 分。另起两条相同交卷请求，得到同一作答编号和一个重放回执。

前置试跑的混合场景有 1 次交卷未获得有效结果。核对数据库只保存了预期 180 条中的 179 条，服务日志无对应 500。该轮没有捕获错误类型，无法确定原因。加上错误类型采集复跑，随后两轮共 1380 次常规请求均成功。

独立库另用固定 200 ms 延迟的本地模型替身实测五个答疑同时发起，收到五次诊断、五次答疑，峰值五个请求在模型调用中，全部交接完成约 614 ms。该读数代表本机模拟提供商条件，实际部署容量和付费模型响应时间需随环境另测。

## 复测

1. 使用名称以 `test_` 开头的独立 MySQL，迁移到当前版本，临时 API 只监听本机 18002。设置该 API 的测试签名密钥并关闭外部模型、判题及维护工作器。
2. 在独立库用[原创演示包](../examples/written/README.md)审核发布 `demo-s-prefix-sum`，记下题库上的数字编号。
3. 在仓库根目录给脚本进程设置同库的 `TEST_DATABASE_URL` 和同一个测试 `JWT_SECRET`，执行 `backend\.venv\Scripts\python.exe tools\bench_written_practice.py --question-id 1`，将 1 替换为数字编号。工具会用新合成身份核对 API 与数据库配对，并打印每组读数与失败类型。测试结束后可清理独立库。
