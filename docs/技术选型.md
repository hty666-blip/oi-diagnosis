## 2. 前后端边界（别把逻辑放错地方）

```
┌──────────────────────────────┐        ┌──────────────────────────────┐
│ 前端（React SPA）             │  REST  │ 后端（FastAPI）               │
│ · 只做展示与交互              │◀──────▶│ · 一切业务规则                │
│ · 不做诊断规则判断            │  SSE   │ · 权限/租户/审计              │
│ · 不直连模型 / 沙箱           │        │ · 调 LLM / 调 judge           │
│ · 状态：Query + Zustand       │        │ · 状态：PG + Redis            │
└──────────────────────────────┘        └──────────────────────────────┘
```

**三条纪律**：

1. **前端不判断"错因"**。错因编码、提示层级全部由后端返回，前端只渲染。否则规则会散落在两边。
2. **前端不持有密钥**。模型 Key、judge token 只在后端。
3. **类型靠生成，不靠手抄**：

```bash
# 从 FastAPI 的 /openapi.json 生成 TS 类型
pnpm dlx openapi-typescript http://localhost:8000/openapi.json -o web/src/api/schema.d.ts
```

这一步能让"后端改字段、前端编译报错"，是 1 人项目最值的自动化。

## 3. 前端关键实现点

### 3.1 页面骨架（6 个就够）

| 页面 | 核心交互 |
|---|---|
| 提交/诊断页 | Monaco 编辑器 + 题目侧栏 + "开始诊断" + SSE 进度流 |
| 诊断结果页 | 错因卡（机制层/认知层）+ 证据面板（编译日志/反例/计时曲线）+ 提示阶梯 |
| 答疑会话页 | 对话流 + 提示升级按钮（受后端状态机约束）+ 代码块只读 |
| 错题本 | 卡片列表 + 筛选（知识点/错因/时间）+ 导出 PDF |
| 教练工作台 | 待复核队列 + 班级热力图 + 批量查看 |
| 管理/合规 | 监护人同意、数据导出/删除、审计日志 |

### 3.2 SSE 进度流（体验的关键）

```ts
const es = new EventSource(`/api/v1/submissions/${id}/stream`);
es.addEventListener("stage", e => setStage(JSON.parse(e.data)));
es.addEventListener("done", e => { setResult(JSON.parse(e.data)); es.close(); });
es.addEventListener("degraded", e => setDegraded(JSON.parse(e.data)));
```

**规则**：3 秒内必须出第一条 `stage`（否则用户以为卡死），即使后端还在取证。

### 3.3 Monaco 的用法

- 只读模式展示学生代码（诊断结果页），带行号高亮（定位到 `evidence.line`）；
- 编辑模式提交代码，`language="cpp"`；
- **不要**在浏览器里跑代码（安全 + 无意义），一切执行走后端。

### 3.4 状态划分

| 状态 | 放哪 | 例子 |
|---|---|---|
| 服务端数据 | TanStack Query | 诊断结果、题目、班级统计 |
| 跨页 UI 状态 | Zustand | 当前学生、侧栏折叠、编辑器主题 |
| 页面内状态 | useState | 弹窗开关 |

## 4. 后端关键实现点

### 4.1 分层与目录

```
backend/
├─ app/
│  ├─ api/v1/           # 路由（只做参数解析 + 调 service）
│  ├─ services/         # 用例：submit / diagnose / tutor / report
│  ├─ domain/           # 实体、值对象、状态机（纯 Python，可单测）
│  ├─ agents/           # 每个 Agent 一包：schema.py / prompt.md / node.py
│  ├─ capabilities/     # sandbox / static / differ / complexity / rag / kg
│  ├─ orchestrator/     # LangGraph 图定义 + 预算/证据闸门装饰器
│  ├─ gateway/          # 模型网关（路由/重试/计费/脱敏）
│  ├─ infra/            # db / redis / storage / tracing
│  └─ main.py
├─ migrations/          # Alembic
├─ tests/
└─ pyproject.toml
```

### 4.2 一次诊断的调用链（对应架构 §6）

```
POST /submissions
  → service.submit()            # 落库 + 去重 + 入队
  → arq.enqueue(run_pipeline)
  → orchestrator.graph.ainvoke()  # LangGraph
      ├─ guard → parse → route
      ├─ [inspect ‖ probe ‖ hunt]   # 并行
      ├─ diagnose → gate → verify → teach
      └─ checkpoint 每步落 PG
  → SSE 推送 stage/partial/done
```

### 4.3 沙箱客户端（薄封装，不重写）

```python
class SandboxClient:
    async def compile(self, code: str, *, flags: list[str] | None = None) -> CompileResult: ...
    async def run(self, exe_id: str, stdin: bytes, *,
                  time_ms: int = 2000, memory_mb: int = 512) -> RunResult: ...
```

只做三件事：拼 `/run` 请求、超时控制、把 go-judge 的返回映射成领域对象。**不要**在这里加业务逻辑。

### 4.4 为什么是 arq 而不是 Celery

| 维度 | arq | Celery |
|---|---|---|
| async | 原生 | 需桥接，容易踩坑 |
| 依赖 | 只要 Redis | Redis/RabbitMQ + 一堆 |
| 可视化 | 无（自己写） | Flower 现成 |
| 简历 | 小众 | 更常见 |

**结论**：毕设用 arq（省心）；如果团队已有 Celery 经验，把 `TaskQueue` 接口换实现即可（架构里已抽象）。

---

### 4.5 关于 LangChain：用零件，不用框架

先澄清一个常见误解：**LangGraph 就是 LangChain 团队做的**，而且 `pip install langgraph` 会连带安装 `langchain-core`。所以"用不用 LangChain"这句话得拆开看：

| 层 | 包 | 用不用 | 理由 |
|---|---|---|---|
| 编排（状态图） | `langgraph` | ✅ **用** | checkpoint / interrupt / streaming 现成，省 2~3 周 |
| 核心抽象（消息、工具、Runnable） | `langchain-core` | ✅ 间接用 | LangGraph 的依赖；消息类型统一，不吃亏 |
| 文档切分 | `langchain-text-splitters` | ✅ **用** | 按标题递归切分，中文 RAG 省一天 |
| 模型客户端 | `langchain-openai` 等 | ⚠️ 可选 | 我们要多厂商路由 + 计费 + 脱敏 + 缓存，自研 `ModelGateway` 更合适；底层仍是 OpenAI 兼容协议 |
| 高层 Chain / `AgentExecutor` | `langchain` | ❌ **不用** | 抽象重、黑盒、难调试；官方也建议新项目直接上 LangGraph |
| 观测 | LangSmith（商业 SaaS） | ❌ 不用 | 数据出境 + 收费；用自托管 Langfuse |
| 评测 | `langchain.evaluation` | ❌ 不用 | 它评的是通用问答质量，我们要的是"诊断准确率/证据覆盖率/答案泄露率" |

**一句话：LangGraph 做骨架，langchain-core 做零件，`langchain` 的高层抽象不用。**

为什么不直接 `create_react_agent` 三行搞定：

1. **流程必须是确定性的**。诊断不是"模型自己决定下一步"，而是"置信度低就转人工、评审打回就重诊、超时就降级"——这些是代码约束，不是提示词。
2. **需要预算与截止时间**。ReAct 循环不给你 token 上限，也不保证 45 秒内返回。
3. **需要证据闸门与中间产物落库**。"没有证据不许定因"这条，框架层根本没有对应概念。

> 反过来说：如果做通用聊天机器人，`create_react_agent` 三行就够；但我们要的是**可审计的教学行为**，所以必须显式建模。这也是答辩时"为什么不用现成 Agent 框架"的标准答案。

## 5. 本地开发（Windows）

```powershell
# 1. 基础设施（WSL2 + Docker Desktop）
docker compose -f deploy/compose.dev.yml up -d postgres redis minio judge

# 2. 后端
cd backend
python -m venv .venv; .venv\Scripts\activate
pip install -e ".[dev]"
alembic upgrade head
uvicorn app.main:app --reload --port 8000

# 3. 前端
cd web
pnpm install
pnpm dev          # http://localhost:5173，代理 /api 到 8000
```

**注意**：`go-judge` 必须跑在 Linux 容器里（Windows 原生为实验性支持）；开发期用 Docker 暴露 `5050` 即可，业务代码无感知。

## 6. 为什么不选另外那些

| 备选 | 否决理由 |
|---|---|
| **Next.js** | 本项目是登录后的后台系统，不需要 SSR/SEO；引入 RSC 只会增加心智负担 |
| **Vue 3 + Element Plus** | 也好用，但简历通用性弱于 React；shadcn 的组件可改性更适合"要做个像样 demo" |
| **Redux** | 服务端状态用 TanStack Query 就够；Redux 的样板代码是纯成本 |
| **Django + DRF** | admin 很香，但异步/流式/LLM 调用都别扭；诊断链路是长任务 + SSE，FastAPI 更顺 |
| **Flask** | 太裸，校验/文档/异步都要自己拼 |
| **Node/NestJS 全栈** | 前后端同语言是优点，但 Python 的 LLM/数据处理生态明显更强，且沙箱/评测脚本本来就偏 Python |
| **微服务 / K8s** | 1 人 12 周，纯负收益（架构 ADR-001 已论证） |
| **MySQL** | pgvector 是决定性因素，少一个向量库 |
| **Celery** | 见 §4.4 |

## 8. 题库当前状态（已落地）

```bash
# 已跑通：洛谷题面导入（仅本地演示用）
python tools/luogu_tags.py                      # 标签映射（一次）
python tools/luogu_import.py --ids P1001,P1046 --delay 2.0
```

**已完成**：26 道题（NOIP 普及组为主），31 组样例，48 条标签映射。详见 [tools/README](../tools/README.md)。

- 输出：`data/problems/<pid>.json`（含 `markdown`、`samples`、`difficulty`、`tags`、`source_url`、`license_note`）
- 每条标记 `package_level: "C"`、`has_testdata: false` —— **只有题面，没有测试数据**
- 合规：题面版权归洛谷/出题人，仅本地演示、不公开分发；脚本内置限速（≥1s）与退避
- 实现：走洛谷前端的 content-only 接口（`x-lentille-request: content-only`），拿到的 JSON 比解析 HTML 稳定；失败回退 HTML 解析

> 这意味着：爬来的题**只能走"静态分析 + 讲解"路径**，用不了对拍/反例最小化。要演示完整诊断，仍需按架构 §9.6 自建 20~40 道带 validator 的题包。

## 9. 12 周学习成本评估

| 技术 | 你的熟悉度假设 | 上手成本 | 风险 |
|---|---|---|---|
| React + TS + Tailwind | 会用 JS | 3~5 天 | 低 |
| FastAPI + Pydantic | 会 Python | 2~3 天 | 低 |
| SQLAlchemy async | 用过 ORM | 2 天 | 中（async 会话易踩坑） |
| LangGraph | 没用过 | 3~4 天 | 中（概念多，但文档好） |
| go-judge | 没用过 | 2 天 | **中高（privileged 容器 + 编译脚本）** |
| pgvector + RAG | 没用过 | 2 天 | 低 |

**结论**：技术栈本身不构成风险，**唯一的高风险是 W1~W2 的沙箱联调**——所以架构排期把它放在第一周。
